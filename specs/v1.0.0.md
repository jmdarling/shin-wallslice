# v1.0.0 — Ready for your NAS

Status: ready

Make shin-wallslice easy to install and maintain through public container releases, with Unraid 7.2.3 as the primary first-install target. Establish verified releases, Community Applications submission materials, and an automatic GitHub issue-to-PR workflow without expanding the wallpaper feature set.

## Feature: Continuous integration

Every proposed change receives repeatable checks in GitHub Actions, including changes made by agents.

### Acceptance criteria

- [x] Pull requests and pushes to the default branch run lint, formatting checks, explicit strict TypeScript checks, server tests, Lit Chromium browser tests, and production builds. Failures appear as actionable GitHub checks and prevent the verification workflow from succeeding.
- [x] CI uses Node.js 24, the repository-pinned pnpm version, frozen-lockfile installation, and the browser dependencies required by Playwright. Tests require no live AI credentials or external AI service.
- [x] Container verification exercises production HTML/assets, health checks, non-root execution, configuration overrides and failures, image processing, and downloads. Persistent preferences are verified across container replacement using the same data mount.
- [x] Linux amd64 and arm64 image builds and runtime smoke checks run before those architectures are promoted into a stable published image. Emulated verification is identified as such in the evidence.
- [x] Fork pull requests can run ordinary verification without publication or agent secrets. Workflow permissions are scoped to each job; third-party actions are pinned to reviewed commit SHAs with readable version annotations.
- [x] Required-check names and default-branch protection setup are documented and verified where repository access permits. Missing GitHub account settings are reported explicitly rather than presented as configured.

## Feature: Verified public container releases

Publishing a stable GitHub Release such as `v1.0.0` triggers verification and publication to `ghcr.io/jmdarling/shin-wallslice`. Installing or updating the app never requires a source checkout, a local build, or registry login.

### Acceptance criteria

- [x] A stable GitHub Release triggers the release workflow. It validates the semantic version, verifies that root/client/server package versions agree with the release, and rejects invalid or mismatched versions with a clear failure.
- [x] The initial release consistently identifies itself as 1.0.0 in package metadata, image metadata, release notes, and installation examples; stale 0.2.0 package versions are corrected. Future version-bump steps are documented.
- [x] Verification succeeds for the released source before stable image tags are updated. A failed verification or architecture build leaves the existing stable aliases unchanged and exposes useful workflow diagnostics.
- [x] One public multi-platform image supports `linux/amd64` and `linux/arm64`, retaining Node.js 24, one Fastify process/port, no dependent service containers, flat-file `/data` persistence, and non-root application execution.
- [x] Stable releases publish exact version tags such as `1.0.0`, major/minor aliases such as `1` and `1.0`, and `latest`. Exact release tags are not silently overwritten with different artifacts. Pre-releases and non-release pushes never move stable aliases; older release reruns cannot roll `latest` back inadvertently.
- [x] Stable aliases point to the verified multi-platform artifact. Anonymous pulls of the published image and architecture manifest inspection succeed, and post-publication smoke verification records the released digest.
- [x] OCI metadata identifies the source repository, release version, revision, and MIT license. Published images include build provenance and an SBOM, with documented inspection commands.
- [x] Runtime image contents exclude local configuration, credentials, test fixtures, and unnecessary development tooling. The release records a container vulnerability scan and explains any unresolved material findings.
- [x] GitHub Actions publishes with narrowly scoped credentials, preferring its repository token for GHCR. One-time package visibility and repository-permission requirements are documented and checked; public repository visibility alone is not assumed to make the package public.
- [x] Release notes link to installation instructions and identify image tags/digest, changes, compatibility considerations, and rollback steps. A failed publication has a documented retry/recovery procedure without rebuilding or replacing an already published exact release silently.

## Feature: Easy Unraid installation and operation

Provide a prefilled Docker template and a short walkthrough for Unraid 7.2.3. A new installation works before Community Applications approval, and the same application can later be installed from Apps when listed.

### Acceptance criteria

- [x] A version-controlled Unraid Docker XML template uses the public GHCR stable image, bridge networking, an editable host port mapped to container port 3000, a working WebUI link, an app icon, project/support links, and a dedicated appdata mapping to `/data`. Privileged mode is off.
- [x] A fresh default appdata directory created through Unraid's installation flow is writable by the application's non-root runtime identity without manual `chown`, `chmod`, world-writable permissions, or privileged execution. The actual identity/permission mechanism is documented and tested; unsupported `PUID`/`PGID` variables are not advertised.
- [x] Docker named-volume installation remains functional, and existing UID/GID 1000 data remains usable or has an explicit, bounded migration procedure. Ownership adjustments, if any, do not modify unrelated host directories.
- [x] Default installation needs only the normal port/path choices and has AI disabled. Optional AI connection settings are clearly labeled advanced fields with no real credentials or misleading defaults; a read-only partial JSON mount remains supported without being required for first run.
- [x] Template descriptions explain memory and temporary-storage expectations, writable temporary storage, persistent preferences versus ephemeral images, and safe use on a trusted LAN. Runtime configuration defaults and precedence remain consistent with AGENTS.md.
- [x] Before listing approval, a user can obtain the supplied template through a complete, copyable procedure, select it in Unraid, apply it, and open the WebUI. Any required template-import terminal step is short and explicit; building images, installing Git/Node, editing XML, and terminal permission repair are unnecessary.
- [x] Instructions cover changing a conflicting host port, enabling autostart, checking health/logs, updating through Unraid, pinning an exact version, rolling back, and preserving appdata during replacement. They explain that publishing an image makes updates available but does not automatically update the user's server.
- [ ] A real Unraid 7.2.3 walkthrough verifies template installation, WebUI access, upload/cropping/PNG and ZIP download, restart, and preference persistence through container replacement. Record the tested image digest and observations. If access to the developer's NAS is unavailable, provide a short guided checklist and keep this criterion unchecked until actual verification occurs.

## Feature: Automatic owner issue-to-PR execution

New issues filed by `jmdarling` automatically start Codex through GitHub Actions using an OpenAI API key. Outside reports remain available for normal issue discussion and start agent work only through an explicit maintainer action. Agent output is a reviewable PR; merging remains a human decision.

### Acceptance criteria

- [x] GitHub issue forms capture reproducible bug reports and actionable feature requests, including expected behavior, actual behavior, relevant version/environment, and success criteria. Instructions ask reporters to redact secrets and private data.
- [ ] Opening an issue as `jmdarling` starts one agent attempt without requiring a label, comment, or initial triage. An issue from another author does not start a paid run automatically. A documented maintainer-only trigger can start work for an existing issue, including an outside report.
- [x] Author and trigger permissions are checked from trusted GitHub identity data. Issue text, labels supplied by outsiders, bot posts, and quoted instructions cannot grant authorization. Issue content is passed as task data without shell interpolation.
- [ ] Codex receives the issue and applicable repository instructions, installs the pinned development dependencies, makes scoped changes on a dedicated `codex/` branch, runs relevant checks, and opens a PR linked to the issue with a clear description and validation evidence.
- [ ] Ambiguous or unworkable issues result in a concise issue comment explaining the missing information or blocker. The agent does not invent requirements, mark incomplete work successful, or close the issue merely because a run ended.
- [ ] Generated PRs receive the same required CI as human PRs. Token/event restrictions that can suppress workflows on bot-created PRs are handled and verified; tests executed only inside the agent job are not substituted for the required PR checks.
- [ ] Runs have documented configurable time/turn bounds, bounded concurrency, and no unlimited retry loop. Duplicate events and manual reruns do not create duplicate PRs; a maintainer can cancel, retry, and disable automation. Failure and missing-credential states are visible and actionable without exposing secrets.
- [x] The agent cannot merge PRs, publish releases/images, change repository settings, or use release credentials. PRs changing workflows or instructions remain subject to human review, and any job running proposed code has only the credentials needed for that phase.
- [x] A maintainer guide documents API billing separately from ChatGPT subscriptions, required OpenAI and GitHub secrets/settings, the selected configurable model, credential rotation, trigger behavior, cancellation/retry, and troubleshooting. No API keys are committed or collected in public issues.
- [ ] End-to-end verification demonstrates an owner issue producing a linked PR with functioning CI, an outside issue being skipped automatically, a maintainer-triggered attempt, duplicate-event handling, and a controlled failure. Use dedicated clearly identified test issues/PRs and record outcomes without secrets.

## Scope and verification references

This version distributes the existing wallpaper functionality. It does not add authentication, multi-user isolation, new wallpaper features, automatic merging, remote deployment to the developer's NAS, or automatic installation of updates on user servers. Real publication and end-to-end verification belong to implementation; this spec alone does not configure GitHub, publish artifacts, or submit a listing.
