# v1.1.0 — A considered visual identity

Status: implemented

Explore three distinct design directions for shin-wallslice, present static mockups for developer selection, then fully implement the selected direction. Preserve the successful Input → Processing → Download workflow and existing capabilities while improving the visual design.

## Feature: Three comparable design directions

Use the frontend-design skill to audit the current interface and develop three deliberate visual identities grounded in wallpaper framing and device output. The current green identity and screen layouts may be replaced. All directions must be feasible within the existing Lit application and Web Awesome design system; `ui.excalidraw` remains guidance for the workflow rather than a visual constraint.

### Acceptance criteria

- [x] Present a concise audit of the current interface, identifying concrete visual problems and how each proposed direction addresses them without changing the three-stage workflow or removing capabilities.
- [x] Present exactly three named directions with meaningfully different typography, composition, control treatments, and image presentation. Palette swaps alone do not count as distinct directions.
- [x] Each direction includes a compact design plan: 4–6 named core colors with hex values, typefaces and their roles, a layout concept with alignment guidance and a simple wireframe, and principles explaining its fit for shin-wallslice. Describe practical tradeoffs and give a reasoned recommendation without selecting for the developer.
- [x] Review each plan against the brief and the frontend-design skill before producing mockups; revise generic or decorative choices that lack a purpose in this application.
- [x] Each direction includes static mockups of Input, Processing, and Download at both desktop and mobile sizes in both light and dark appearances: 12 primary mockups per direction, 36 total. Clearly label direction, screen, viewport, and appearance, and provide a comparison index with readable full-size views.
- [x] Use the same representative source wallpaper, selected devices, settings, and output names across directions. Show realistic existing controls and content, including AI-enabled crop choices, spatial anchors, OLEDify, manual framing, naming, and individual/ZIP download actions where relevant, so differences can be evaluated fairly.
- [x] The mockups make primary actions, current stage, selected controls, crop boundaries, and image previews clear. Mobile layouts demonstrate how controls and previews fit without page-wide horizontal overflow or overlapping targets.
- [x] Accompany each direction with representative treatments for visible keyboard focus, disabled controls, pending work, an actionable error, and an upscaling warning. Explain how the design accommodates AI-disabled and AI-pending states. These may be annotated detail views rather than additional full-screen mockups.
- [x] Present mockups as design artifacts rather than interactive prototypes or completed application screens. Keep the production interface unchanged during exploration.

## Feature: Developer selection before implementation

The developer chooses the direction after reviewing the three proposals. This selection is a required decision within implementation of this spec, not a prerequisite for marking this planning document ready.

### Acceptance criteria

- [x] Present all three directions and their comparison before requesting selection through the agent question-and-answer interface, asking one question at a time.
- [x] Pause production UI implementation until the developer explicitly selects a direction. Silence, elapsed time, or the agent's recommendation does not constitute selection.
- [x] Record the selected direction and any requested refinements in this spec, with references to its mockups. Resolve material changes to the selected proposal through focused Q&A before dependent implementation.
- [x] Implement only the selected direction in the application. The three concepts do not become selectable runtime themes.

## Feature: Complete implementation of the chosen design

Apply the selected identity consistently across the application, retaining Lit and Web Awesome. Layout, hierarchy, typography, palette, spacing, component styling, and supporting interface copy may change to serve the chosen design; preserve the established workflow and functional semantics.

### Acceptance criteria

- [x] Input, Processing, and Download match the selected direction and recorded refinements, including headers, navigation, controls, image surrounds, previews, messages, and loading indicators. Record side-by-side visual verification against the selected mockups and explain material adaptations.
- [x] Browser-driven light/dark appearance works on initial render and live preference changes. Both appearances follow the selected identity consistently across Web Awesome components and native controls without changing image colors or exported files.
- [x] File selection, drop and paste, device selection, entropy and optional AI framing, all five anchors, independent pointer/touch/keyboard crop positioning, per-device reset, OLEDify and its loading feedback, AI naming and manual name edits, folder organization, and individual PNG/ZIP downloads retain their existing behavior.
- [x] Back navigation, Start over, saved preferences, AI fallback and recovery, errors, warnings, and pending work remain understandable and usable. Presentation changes do not reset workflow state or interrupt processing.
- [x] Verify all three screens at representative desktop and mobile widths, including 390px and 320px. Controls, long device names, filenames, and status messages remain usable without page-wide horizontal overflow, clipped actions, or overlapping content.
- [x] Normal text meets at least 4.5:1 contrast, large text at least 3:1, and essential control boundaries and focus indicators at least 3:1 against adjacent colors in both appearances. Selection is distinguishable without color alone; controls retain accessible names, semantics, visible keyboard focus, and usable pointer/touch targets. Any introduced motion respects reduced-motion preferences.
- [x] Exercise a real source image through the complete workflow and verify exported dimensions, framing, OLEDify results, filenames, and ZIP organization match the current functionality. Update meaningful Lit Chromium tests where presentation or interaction changes affect existing coverage.
- [x] Root lint, formatting checks, explicit TypeScript checks, tests, builds, and distribution checks pass. Record executed checks and visual verification in this spec, including any remaining limitations; do not mark the version implemented while required work remains.
