# v0.1.0 — Project scaffold

Status: ready

Establish a runnable foundation for shin-wallslice with separate TypeScript client and server packages in a pnpm workspace. This version delivers a styled placeholder page, a server health endpoint, local development and verification tooling, JSON runtime configuration, and a single Docker image.

Wallpaper processing and application persistence are outside this version's scope. GitHub Actions CI, image publishing, and an Unraid Community Apps template are deferred.

## Feature: Development workspace

Use TypeScript for both the Lit client and Fastify server, maintained as separate packages within one repository. Use pnpm for dependencies and workspace management, with a pinned pnpm version and committed lockfile. Use Node.js 24 LTS consistently for local development and Docker.

Use Vite for client development and production builds, preferring its ecosystem where suitable. Enable strict TypeScript checking and ES modules throughout. During server development, compile TypeScript in watch mode and restart compiled JavaScript with Node.js watch mode.

### Acceptance criteria

- [x] The repository contains separate client and server packages, both using strict TypeScript and ES modules.
- [ ] The repository declares Node.js 24 as its supported runtime and pins its pnpm version; a pnpm lockfile is committed.
- [x] Dependencies can be installed from the repository root with pnpm using the committed lockfile without changing it.
- [x] Documented root commands start both packages for local development and build both packages for production.
- [x] Client changes update the browser automatically during local development, and API requests from the Vite development server reach Fastify through a proxy.
- [x] Server source changes trigger TypeScript recompilation and a server restart through Node.js watch mode.
- [x] Explicit type checking covers both packages independently of transpilation and returns a nonzero exit status for type errors.
- [x] AGENTS.md records the agreed technology choices that apply beyond this version.

## Feature: Runnable application baseline

Provide a Lit placeholder page styled with Web Awesome and a Fastify health endpoint. In production, one Node.js process running Fastify serves the built client assets and API through one exposed port.

### Acceptance criteria

- [x] Starting the application displays a shin-wallslice placeholder page that uses Lit and Web Awesome styling or components.
- [x] A documented server health endpoint responds with HTTP 200 and a JSON response indicating that the server is running.
- [x] Starting the production build serves the placeholder page, its assets, and the health endpoint on the same port through Fastify without running the Vite development server.

## Feature: Local verification tooling

Use Vitest across both packages. Test the server through Fastify request injection and Lit components through Vitest Browser Mode with Playwright and Chromium. Use ESLint with typescript-eslint for linting and Prettier for formatting.

Keep verification local for this version, including a Docker smoke check.

### Acceptance criteria

- [x] Documented root commands run linting, formatting checks, type checks, tests, and production builds across the workspace, reporting failures with nonzero exit statuses.
- [x] A Vitest server test verifies the health endpoint's status and JSON response using Fastify request injection.
- [x] A Vitest Browser Mode test using Playwright and Chromium verifies that the Lit placeholder renders its visible application identity.
- [x] Documentation explains how to install the browser required by the tests and run all local checks from a clean checkout.
- [x] A documented local Docker smoke check verifies that the running container serves the placeholder page, its assets, and the health endpoint.

## Feature: JSON runtime configuration

Ship documented default application runtime configuration. In Docker, allow a read-only file mounted at `/config/config.json` to replace the bundled configuration. Validate the effective configuration at startup. Development and build tools may use their native configuration formats.

### Acceptance criteria

- [x] The application starts with documented bundled JSON defaults when no replacement configuration is provided.
- [x] A valid replacement JSON file mounted read-only at `/config/config.json` is used in place of the bundled configuration; changing a documented runtime setting changes the application's behavior after restart.
- [x] Malformed JSON or invalid runtime configuration prevents startup, returns a nonzero exit status, and produces a clear diagnostic identifying the configuration problem.
- [x] Documentation describes available settings, their defaults, the replacement behavior, and local and Docker configuration usage.

## Feature: Docker deployment

Package the compiled server and built client as a single Docker image suitable for home NAS deployment, with no runtime dependency on another container or external service. Support Linux amd64 and arm64, and run the application as a non-root user.

Reserve `/data` as the location for future persistent application files without introducing persistence behavior in this scaffold.

### Acceptance criteria

- [x] Documented local commands build the Docker image and start a container from it.
- [x] The Docker build supports Linux amd64 and arm64 images and uses Node.js 24 LTS for the application runtime.
- [x] The application process runs as a non-root user.
- [x] The running container serves the placeholder page and health endpoint through one exposed port without additional containers or external services.
- [x] Documentation includes the read-only configuration mount, port mapping, runtime user and file permission requirements, and the reserved `/data` location for future persistent files.
