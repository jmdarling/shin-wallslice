# v1.3.1 — Unified OLEDify working toast

Status: implemented

Integrate active OLEDify status into the existing loading toast. Use one toast for
AI cutoff tuning and every OLEDify-triggered preview render, while keeping results
and failure/Retry feedback inline.

## Feature: One toast for active OLEDify work

Show the existing nonblocking OLEDify toast while AI cutoff tuning or an
OLEDify-triggered render is pending or running. Rendering includes threshold
changes, switching OLEDify on or off, and applying automatic per-image defaults or
an AI recommendation when that changes the previews. This expands the earlier
threshold-only toast behavior.

### Acceptance criteria

- [x] An automatic AI cutoff search and each explicit Retry show the toast while tuning is pending or running. AI-disabled, skipped, and already-completed analysis do not show a working toast by themselves.
- [x] Threshold changes, on/off switch changes, and automatically applied OLEDify choices show the toast when they schedule changed previews and outputs. Feedback begins during any debounce or queued render, without requiring an Apply action.
- [x] Toast text distinguishes AI cutoff tuning from preview/output rendering. When both are active, one toast communicates both phases; competing OLEDify toasts are never displayed.
- [x] The toast remains visible while either OLEDify task is active. Completing one task does not hide the other task's progress. After an automatic recommendation schedules a render, progress continues until the current previews and outputs are ready.
- [x] Rapid edits and superseded render responses cannot dismiss the toast early or replace current outputs. A render is complete only when the latest accepted settings have completed through the existing preview/export lifecycle.
- [x] Remove duplicate inline OLEDify working announcements from Processing and Download. Keep the local classification/fallback explanation, completed recommendation (including off), skipped/AI-disabled explanation, and manual-control protection visible inline as relevant.
- [x] Successful or skipped work leaves no persistent progress toast. If analysis or rendering fails, its working state ends and existing inline error and Retry controls remain available. If the other task is still active, the toast continues to describe that work rather than implying success.
- [x] The toast works on Processing and Download and follows active work across navigation without restarting it. Start over, image replacement, job expiry, and shutdown clear or invalidate the previous image's progress so stale work cannot show a toast for another workflow.
- [x] The toast does not capture focus or block pointer, touch, or keyboard access to controls. Its loading indicator and phase text remain readable and within the viewport on desktop and narrow mobile layouts in light and dark appearances, with polite accessible status announcements.
- [x] Toast visibility alone does not make the workflow busy. Users retain manual OLEDify control and can navigate, download, and save current completed outputs while AI tuning runs; existing safeguards still prevent exports from incomplete or superseded renders.
- [x] Preserve the existing 15%/32 candidate rule, cutoff 16 local fallback, bounded AI search, protected manual choices, crop positions, naming, and pixel transformation. Unrelated crop/device rendering and naming/detection tasks do not independently trigger an OLEDify toast.
