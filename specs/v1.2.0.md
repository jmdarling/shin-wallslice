# v1.2.0 — Save wallpapers to your server

Status: implemented

Add an optional, on-demand way to write generated wallpapers directly to a configured directory on the server. Use the same PNG files, naming, and folder organization as the existing ZIP export while retaining browser downloads.

## Feature: Configured server output directory

The operator configures one output directory through runtime configuration. The browser does not accept destination paths. Server saving is disabled by default and becomes available when an output directory is configured.

### Acceptance criteria

- [x] Provide an optional output-directory setting through partial JSON configuration and a corresponding `SHIN_WALLSLICE_` environment override. Follow the existing configuration precedence, relative-path resolution, read-only JSON support, and startup validation conventions. Invalid supplied values produce clear startup errors without exposing credentials.
- [x] An installation without an output directory continues to support the existing workflow and downloads without requiring a new mount or configuration. Server saving is unavailable in both the UI and API while unconfigured.
- [x] The UI offers no destination-path input, and save requests cannot select a different root directory. Generated paths stay within the configured destination; unsafe names or symbolic links cannot redirect writes outside it.
- [x] Support local Node.js installations and non-root Linux amd64/arm64 container deployments. Document `/data/output` as a container destination that can use the existing persistent data mount or a dedicated host bind mount. Do not require a database or another container.
- [x] Create missing destination/device directories when permissions permit. An unavailable, unwritable, or full destination produces an actionable error; it does not prevent ordinary browser downloads.

## Feature: Save current wallpapers alongside ZIP download

Add **Save to server** beside **Download ZIP** on the Download screen when configured. The action saves all currently selected device outputs using the current wallpaper name and the existing **Organize into device folders** choice.

### Acceptance criteria

- [x] Saving occurs only when the user chooses **Save to server**. Generating previews, changing settings, downloading, or navigating does not automatically write to the output directory.
- [x] With folder organization off, save `<safe-name>-<device-id>.png` directly in the configured directory. With it on, save `<device-id>/<safe-name>.png` beneath that directory. Do not add a wallpaper-level wrapper directory or save a ZIP file.
- [x] Use the same safe-name normalization, fallback name, selected device set, and PNG contents as a ZIP export of the same current render. Saved wallpapers match the final previews in framing, dimensions, and OLEDify settings.
- [x] Save only current, completed outputs. Pending, failed, expired, or superseded renders cannot save stale images. An accepted save uses a consistent render, name, and folder-layout selection throughout the operation.
- [x] Show pending feedback, prevent duplicate submissions while saving, and announce success or failure accessibly. Success identifies the destination and saved files. A failed or partially completed save is not reported as complete; feedback identifies what was saved and what failed so the user can recover.
- [x] The action and its feedback remain usable by keyboard and on desktop and narrow mobile layouts in both light and dark appearances.
- [x] Existing individual PNG and ZIP downloads remain available and retain their behavior. Back navigation and Start over continue to work.
- [x] Saved files are persistent user output. Job expiry, Start over, temporary-file cleanup, application restart, and container replacement with the destination mount retained do not delete them. Later saves do not remove unrelated files or old outputs for unselected devices.

## Feature: Confirm replacement of existing files

Before a save replaces existing destination files, show the conflicts and ask the user to confirm. Never overwrite a conflicting file solely because the initial save action was chosen.

### Acceptance criteria

- [x] A save with no conflicts completes without an overwrite prompt. A save with conflicts lists the relative paths that would be replaced and offers explicit Replace and Cancel actions before writing any files from that save.
- [x] Cancel leaves all destination files unchanged. Confirm replaces only the listed conflicts and writes the remaining outputs for that save, preserving unrelated files.
- [x] Confirmation applies to the specific save being reviewed. Changes to the render, name, layout, or conflict set cannot reuse approval to overwrite different files; newly detected conflicts require renewed confirmation.
- [x] A conflicting directory or other destination that cannot be safely replaced is reported clearly rather than deleted recursively or treated as an ordinary PNG file.

### Implementation

- Optional `outputDirectory` / `SHIN_WALLSLICE_OUTPUT_DIRECTORY`, following the
  existing single-file precedence, process-relative paths, read-only JSON, and
  environment validation. Defaults omit the setting. Output and temporary storage
  must be separate and non-nested, including through existing symlink ancestors,
  so scratch cleanup cannot remove saved wallpapers.
- On-demand save of the completed current render, sharing ZIP naming and PNG
  bytes. The browser supplies only the name, folder choice, and optional reviewed
  replacement token; it cannot supply destination paths or device IDs.
- Preflight conflict review uses a server-signed token bound to the job, revision,
  normalized name, layout, output paths, and existing-file identity/metadata.
  Changed conflicts require a new review before writes. Writes use exclusive
  staging and no-clobber publication for new files, and replacement of only
  reviewed regular files. Symbolic links, directories, special files, and hard
  links are rejected. Linux pins destination directories with open descriptors;
  local POSIX hosts without `/proc` use a child process with a pinned, identity-
  checked working directory. Both avoid following swapped parent paths for writes.
- Pending/duplicate prevention, accessible conflict/success/failure feedback,
  saved/not-saved file lists, and explicit Replace/Cancel. Existing ZIP/PNG exports
  and navigation are retained. Persistent outputs are independent of job cleanup.
- README, partial JSON example, Compose guidance, Unraid guide/template, persistence
  harness, and real Download screenshots updated. Local output is ignored by Git
  and excluded from Docker build context. The optional destination remains disabled
  in the default deployment examples.
