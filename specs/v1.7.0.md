# v1.7.0 — Unified activity dock

Status: implemented

Replace the app's scattered operational notifications with one consistent activity
dock across Input, Processing, and Download. Users can follow work, inspect its
outcome, and recover from failures without searching different parts of the page.

## Feature: One home for operational notifications

Use the selected Activity dock design direction: a compact bottom-anchored summary
that expands into a list of activities. Retain the existing Web Awesome visual
language, typography, and light/dark appearances. The Processing exploration is
the design reference; the same behavior applies across all workflow steps.

### Acceptance criteria

- [x] Upload/preparation, preview rendering, OLEDify processing and analysis, AI naming, subject detection, preference-load/save failures, initial application-load failures, downloads, and server saves report operational progress and outcomes through the dock. Remove their separate progress strips, error banners, inline operational notices, and OLEDify-only floating message. An operation is never announced or displayed twice in competing notification surfaces.
- [x] Each operation has a clear label, readable state, and optional detail or action using consistent spacing, icons, and wording. Distinguish working, completed, needs-attention, and failed states with text or symbols as well as color.
- [x] An operation updates its existing entry as it progresses, succeeds, or fails. Independent concurrent activities remain individually identifiable. Rapid crop or threshold adjustments coalesce into the current rendering activity rather than flooding the dock with entries.
- [x] Progress accurately describes known work; do not invent percentages. Success means the reported operation actually succeeded. A browser download may report that a file was prepared or handed to the browser, but must not claim that it was saved to disk when that cannot be observed.
- [x] Persistent field guidance and current values remain near their controls, including recommended dimensions, selection requirements, crop/upscaling guidance, and applied OLEDify settings. Operational messages and their recovery actions use the dock; moving notifications does not remove information needed to understand or use a control.
- [x] The dock remains in a predictable location across steps, with a compact idle state when no activity remains. Its expanded list supports inspecting multiple entries without making workflow controls or crop editing inaccessible, including on narrow screens.

## Feature: Compact presentation and current-wallpaper history

The dock stays collapsed until the user explicitly expands it. Its summary shows
activity counts and a spinner while work is running. Only the user expands or
collapses the dock. History is
limited to the current wallpaper, with unresolved application-wide errors retained
when starting over.

### Acceptance criteria

- [x] Working activities update the compact summary with an accurate active count and a visible spinner. The spinner disappears when no work remains. Unresolved failures or required decisions remain evident and take precedence over an all-complete message.
- [x] Completed operations update the compact summary and remain in current-wallpaper history without automatically expanding the dock.
- [x] New errors and required decisions update the compact attention count without expanding the dock or moving focus. Their details and recovery actions are available after explicit expansion.
- [x] Manual expansion stays open until the user collapses it. Progress, completion, failures, hover, and focus do not automatically change expansion. Start over resets the dock to collapsed.
- [x] Completed or failed entries can be dismissed without cancelling work, undoing results, or treating a failure as resolved. Working entries cannot be mistaken for cancellable operations; collapsing the dock leaves all work running.
- [x] Moving between Input, Processing, and Download retains the current wallpaper's activity and results. Start over clears that wallpaper's entries, including dismissed history, and late responses from it cannot repopulate the dock or affect the next wallpaper.
- [x] Unresolved application-wide errors, such as failed preference saves, survive Start over and remain discoverable even if previously dismissed. Successful recovery clears their unresolved state. A new wallpaper does not inherit old wallpaper-specific failures.
- [x] Notification history is not persisted across reloads or application restarts. After reload, fresh failures are reported normally; historical messages are not restored from storage.

## Feature: Useful recovery and detailed outcomes

The dock provides actions specific to the failed operation and enough detail to
understand partial results. Decisions such as replacing existing server files
remain explicit and reviewable.

### Acceptance criteria

- [x] Retry actions name and retry the relevant operation, such as saving preferences, AI naming, subject detection, OLEDify analysis, or rendering. Invalid uploads direct users to choose a valid image; a generic Retry must not run an unrelated load or render operation.
- [x] Retrying updates the relevant activity through working to its new outcome without duplicating errors or leaving a stale failure count. Actions for an expired or superseded wallpaper cannot operate on a newer wallpaper.
- [x] Background AI failures explain any usable fallback and whether the user can continue. Preserve existing local fallbacks, manual-edit protection, and independent AI task behavior while unifying their reporting.
- [x] Server-save results expose the destination and saved/not-saved file details from the dock. Partial saves are clearly incomplete rather than successful, with actionable failure details and the existing safe retry/conflict behavior preserved.
- [x] Existing-file conflicts appear as needs-attention activity with access to an explicit replacement review listing affected paths and offering Replace and Cancel. Replacement never happens through dismissal or automatic retry. The review may use an accessible detail view; it must not introduce a second independent notification system.
- [x] Errors remain available until dismissed or resolved, and detailed results remain inspectable during the current wallpaper. Display safe user-facing explanations without leaking credentials or raw sensitive server diagnostics.

## Feature: Accessibility, documentation, and verification

Make the dock usable with keyboard, touch, and assistive technology, and update
usage guidance to show where feedback and recovery actions now live.

### Acceptance criteria

- [x] The summary, expansion control, dismiss controls, details, and recovery actions have accessible names and visible keyboard focus. Expanded state is exposed programmatically; opening or updating a notification does not steal focus.
- [x] Announce meaningful activity transitions politely and urgent failures appropriately, without duplicate live-region announcements or announcing every polling response or crop adjustment. Completion details remain available after transient presentation ends. Reduced-motion preferences are respected.
- [x] Verify readable contrast, non-color status cues, touch targets, wrapping of long messages/paths, and access to all entries and workflow actions on desktop and narrow mobile layouts in both appearances. Expanded content must not trap focus or make dismissal/recovery unreachable.
- [x] Update the README's workflow, AI behavior, server-save guidance, and troubleshooting instructions to explain the dock, progress/completion behavior, current-wallpaper history, dismissal versus resolution, and operation-specific recovery. Examples must match actual labels and behavior.
- [x] Refresh affected README screenshots and their capture notes in `docs/images/README.md` where the changed interface makes them inaccurate. Verify affected image references, links, and usage examples. Review setup/configuration and persistence guidance; record why no updates are necessary if those behaviors remain unchanged, or update affected instructions if implementation changes them.
- [x] Add meaningful Lit Chromium coverage for concurrent operations, in-place transitions, coalesced renders, manual-only expansion/collapse, collapsed working spinner, non-expanding errors and completions, dismissal, correct retries, partial saves and replacement review, cross-step history, Start over, late responses, unresolved application-wide errors, and reload behavior. Verify that elapsed time and activity changes do not override manual expansion.
- [x] Verify representative real Input-to-Processing-to-Download flows, including successful work and recoverable failures, with keyboard and desktop/mobile checks. Confirm old notification surfaces are removed, existing crop/download/server-save behavior remains correct, and record verification evidence and limitations.
- [x] Root lint, formatting checks, explicit TypeScript checks, tests, production builds, and distribution checks pass before this version is marked implemented.
