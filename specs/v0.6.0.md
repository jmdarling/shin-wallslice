# v0.6.0 — Local and environment configuration

Status: implemented

Support private local JSON overrides and environment variables for every runtime setting, including the sensitive token used to access OpenAI-compatible endpoints. Make local development and NAS container deployment configurable without editing tracked defaults.

## Feature: Layered JSON configuration

Load bundled defaults, merge one optional JSON override file, then apply environment overrides. Automatically discover `config/local.json` at the repository root for local development and local production starts. Select the JSON override file in this order: an explicit `--config` path, `/config/config.json` when present, then the local file. Only the selected override file is merged with defaults; alternative files are not combined.

This version replaces the previous complete-replacement behavior with partial overrides and supersedes the JSON-only runtime configuration rule in `AGENTS.md`. Keep static JSON defaults and support read-only mounted JSON configuration.

### Acceptance criteria

- [x] Without an override file or application environment variables, local and Docker starts retain their respective bundled defaults, including disabled AI and the existing data and temporary directory locations.
- [x] A repository-root `config/local.json` is discovered automatically by both the documented root development command and local production start command, independently of the server package's working directory. The file is optional, ignored by Git, and excluded from Docker build context and images.
- [x] An explicit `--config` file takes precedence over the mounted and local files; a present `/config/config.json` takes precedence over the local file. A missing explicit file fails startup, while an absent automatically discovered file allows fallback to the next source or bundled defaults. An unreadable or malformed selected file fails startup rather than silently falling back.
- [x] JSON overrides may specify only changed settings. Nested `ai` settings merge by field: supplying `ai.token` preserves a configured or default `ai.enabled`, `ai.baseUrl`, and `ai.model`. Existing valid complete configuration files remain usable.
- [x] Effective configuration is validated at startup using the existing setting types, ranges, and AI requirements. Unknown JSON settings and invalid supplied override values produce clear errors and a nonzero exit status; malformed or invalid lower-priority input is not silently hidden by a higher-priority override.
- [x] Configuration remains read-only to the application, relative configured paths retain their documented process-working-directory semantics, and changes take effect after restarting the application. No in-app settings editor or configuration persistence is introduced.

## Feature: Environment overrides for NAS deployment

Allow every runtime setting to be configured through a documented application-specific environment variable. Environment values override the selected JSON file and bundled defaults, including individual nested AI fields. Credentials stay on the server.

### Acceptance criteria

- [x] Every supported runtime setting has a documented, unambiguous `SHIN_WALLSLICE_` environment variable, including AI enablement, base URL, model, and token. Unrelated process environment variables do not affect runtime configuration.
- [x] With no JSON override file, a container can enable AI and configure its base URL, model, and bearer token entirely through environment variables. A controlled provider verifies that the effective token is used for server-side authentication without requiring live credentials or a real OpenAI request.
- [x] A setting supplied through the environment overrides the same setting in JSON. Nested overrides preserve sibling fields; for example, an environment token can accompany a JSON-configured model and endpoint. An environment value disabling AI overrides JSON enablement and prevents AI requests.
- [x] Numeric and boolean variables are parsed with documented strict rules and validated against existing constraints. Unset variables preserve lower-priority values. Empty supplied values have documented behavior for each relevant type, including how to clear an optional token; invalid values fail startup rather than being ignored or loosely coerced.
- [x] Local and Docker starts use the same precedence and validation rules. The Docker health check uses the effective environment-aware configuration, including an overridden bind address or port, and succeeds for a valid deployment on a changed port.

## Feature: Private credentials and configuration guidance

Provide safe examples for entering credentials locally and through NAS container environment settings. Preserve optional, server-side AI access and the current wallpaper workflow.

### Acceptance criteria

- [x] No real API key is required in tracked files, test fixtures, or shipped defaults. A tracked example uses placeholders and documents copying it to the ignored local configuration file. Existing dotenv files remain excluded from Git and are excluded from Docker build context and images; automatically loading dotenv files is outside this version's scope.
- [x] Tokens supplied through JSON or environment variables never appear in client assets, browser API responses, logs, startup diagnostics, health responses, or user-facing errors. Tests use sentinel secrets to verify successful configuration and failure diagnostics, including malformed JSON and invalid environment input, without disclosing their values.
- [x] README guidance documents source selection, nested merging, environment precedence, every variable's name and parsing rules, restart behavior, and migration from complete JSON replacement. It includes local private configuration and read-only mount examples plus Docker/NAS environment configuration with placeholder credentials.
- [x] Documentation explains that environment variables keep keys out of tracked configuration but remain visible to users with access to container configuration; it does not describe them as a secret vault. The application does not write supplied credentials to preference files or other application-managed persistent data.
- [x] `AGENTS.md` is updated during implementation to permit JSON defaults and overrides plus environment configuration, reflecting the new precedence and private local configuration support.
- [x] Automated tests cover defaults, file selection and fallback, partial and nested merges, environment precedence, strict parsing and validation failures, credential handling, and compatibility with existing complete files. Docker smoke verification covers environment-only configuration and health on an overridden port. Root lint, formatting checks, explicit TypeScript checks, tests, and builds pass.
- [x] The application remains deployable as one non-root Node.js 24 container on Linux amd64 and arm64, with flat-file persistence and no new companion service requirement. Existing local processing remains available with AI disabled.
